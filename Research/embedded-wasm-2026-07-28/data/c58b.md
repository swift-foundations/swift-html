## Does not reproduce on 6.5-dev — the abort appears fixed on main

Follow-up to the envelope correction above. Same package, same target, same SDK family, newer toolchain:

- **Toolchain:** `main-snapshot-2026-07-11` via swiftly — `Apple Swift version 6.5-dev (LLVM 6f2057ffeafd4c6, Swift 83c32e02f71e4bb)`
- **SDK:** `swift-DEVELOPMENT-SNAPSHOT-2026-07-11-a_wasm-embedded` (toolchain/SDK pairing verified against `swiftwasm/swift-sdk-index`)
- **Command:** `swift build --swift-sdk swift-DEVELOPMENT-SNAPSHOT-2026-07-11-a_wasm-embedded --target HTML` in swift-html

**`Render_Primitive.swiftmodule` builds.** That is the module and the exact `each Content` / `Render.View` pack archetype that aborted under 6.3.3 at `ASTContext.cpp:5924`. 189 swiftmodules compiled past the abort point; the build continued to unrelated Embedded language restrictions (`StringLiteralType`, key paths, dynamic casting) rather than crashing.

Reproduced in both debug and release configurations on 6.5-dev. Note this snapshot is an assertions-enabled build (`Build config: +assertions`), so the assertion that fires on 6.3.3 would still be live if the underlying defect were present.

### Caveats

- This is **not** a bisect and I have not identified the fix. It establishes that the abort does not reproduce on this snapshot, not which change resolved it.
- The 6.4 line is untested for this signature: no 6.4-branch Wasm SDK is published. `swiftwasm/swift-sdk-index`'s `tag-by-version.json` maps snapshot Wasm SDKs to 6.5-dev (main) only. So "fixed in 6.4" cannot be asserted from this evidence — only "not present on 6.5-dev".
- The Linux x86_64 release + `-O` + `-enable-default-cmo` configuration originally reported here was not re-run on 6.5-dev. If that configuration is what gates the 6.4 migration, it should be retested directly before this issue is closed.

Suggested disposition: keep open pending a 6.4-line retest, but the migration-blocking assessment may need revisiting if 6.4 carries the same fix.
